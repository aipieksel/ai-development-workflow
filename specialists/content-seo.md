# Structured content and technical SEO

Preserve approved content while validating metadata, routes, schema and migration completeness.

Read the [shared specialist contract](../references/specialist-contract.md),
[task contracts](../references/task-contracts.md) and
[acceptance evidence](../references/acceptance-evidence.md).
This profile is a domain lens for existing stages, not a separate workflow or native agent registration.
Assessment and review are read-only; code writes require assignment by the selected execution stage.

## Use and exclude

- Use when: Markdown/MDX content, seo.yaml/schema.yaml, article migrations or generated service pages are in scope.
- Use when: Canonical URLs, sitemaps, redirects, internal links or structured-data output are affected.
- Exclude: The task requests only general marketing strategy with no implementation or content artefact.

## Discover the actual environment

- Inventory source articles/pages and identify the approved content and metadata owners.
- Read complete relevant source documents before rewriting or extracting facts.
- Find the MD/MDX pipeline, frontmatter/schema rules, templates and route generation.
- Check site locale, URL, canonical and redirect conventions from current project evidence.
- Inspect existing structured data in source and rendered output when applicable.
- Identify actual image availability and distinguish missing assets from invented replacements.

## Domain techniques

- Keep authored content separate from reusable presentation and generated metadata.
- Validate required fields, types, slugs, dates and duplicate identifiers at ingestion.
- Map old URLs to new destinations before changing route structure.
- Generate structured data from real visible content and stable source fields.
- Check current search-engine feature support separately from Schema.org vocabulary validity.
- Preserve optimised/approved headings unless the requested edit authorises their change.
- Reconcile every requested source item with an output or explicit exception.
- Verify links, assets, canonicals and sitemap inclusion on built output.

## Source-grounded content and conversion

Build an inventory of pages, articles, products, guides and real destinations before proposing navigation or generating a site. Distinguish existing content, approved new content and ideas with no content yet. Do not create empty guide/hub pages or dead navigation entries simply to fill a template. For bulk work, maintain source-to-output IDs and reconcile every requested item.

Use the current project source of truth for product capabilities and mutable facts. Keep approved copy and SEO headings intact in visual conversion; changing layout, tabs or typography is not authority to rewrite them. Avoid repeated wrapper headings, redundant labels and generic placeholder copy that duplicate the real content. Label unresolved facts for review in the appropriate authoring artifact rather than inventing a claim.

Review conversion copy in the context of the page: make the next action and choices clear, preserve relevant material limitations, and remove unsupported or redundant cautions only within the requested editing scope. Do not add implementation notes, draft badges or verification instructions to public components merely because the agent needed them during production.

Match related links, icons, imagery and examples to the actual product/workload. A semantically wrong symbol or reused generic example can misrepresent a correct paragraph. Use the owning shared-component system for reviews, FAQs, tabs, code blocks and tables instead of creating alternate visual versions.

For article migrations, preserve code/text, links, media references and required OS-specific command tabs along with separate content and SEO/schema files when that is the project's contract. Validate visible content and generated structured data together; a schema that parses but describes absent content is not acceptable.

## Acceptance evidence

- Requested source items reconcile with produced pages and documented exceptions.
- Metadata/schema validate and agree with visible content and canonical routes.
- Approved content, asset references and internal links survive the build/migration.

## Existing capability integration

- Scope caution: The user's specialised content plugin already owns the writing rules; delegate to it.

- Use the writing or editing tools supplied for the current project.
- Use the current project’s SEO and content-audit tools when supplied.
- Use the design-system builder for page presentation instead of embedding a second style system.
- Refresh company facts from the current source of truth; do not freeze old prices in this lens.

## Failure modes

- Do not invent product capabilities, citations, images or schema claims.
- Do not turn title-length or keyword-position heuristics into guaranteed ranking rules.
- Do not infer absent JSON-LD from a text extractor that removes script elements.
- Do not claim the complete collection migrated without a source-to-output reconciliation.
