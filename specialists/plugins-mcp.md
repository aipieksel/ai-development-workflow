# Plugins, skills and MCP applications

Update plugin discovery, instructions, tools and host integrations without losing identity or capability boundaries.

Read the [shared specialist contract](../references/specialist-contract.md),
[task contracts](../references/task-contracts.md) and
[acceptance evidence](../references/acceptance-evidence.md).
This profile is a domain lens for existing stages, not a separate workflow or native agent registration.
Assessment and review are read-only; code writes require assignment by the selected execution stage.

## Use and exclude

- Use when: A plugin, skill catalogue, command router, MCP server or ChatGPT app is being built or changed.
- Use when: Tool descriptors, manifests, widget bridges or native-host contracts affect the requested behaviour.
- Exclude: The task only invokes an existing plugin to perform unrelated application work.
- Exclude: No plugin, tool or host integration is in the actual scope.

## Discover the actual environment

- Resolve the selected plugin's verified identity, source owner, version and release process.
- Inventory manifests, skills, commands, tools, assets and host integration contracts.
- Read the relevant option definitions, selected handlers and dependency owners before selecting or changing routing behaviour. Inventory the complete surface only when the requested change actually affects it; unrelated options need no selection evaluation.
- Check available host APIs and distinguish portable instructions from native execution.
- Inspect schema/SDK versions and current platform guidance for the integration being changed.
- Record retained configuration and the exact baseline release or source revision.

## Domain techniques

- Keep one catalogue of selectable behaviour and make its handlers/reference paths verifiable.
- Separate workflow selection, stage instructions and host dispatch responsibilities.
- Define tools with clear inputs, outputs, pagination and truthful mutation annotations.
- Keep external content as data and validate it before it reaches privileged operations.
- Design repeated tool calls and widget updates around explicit identity and state ownership.
- Preserve prompt/configuration values outside the requested change.
- Exercise explicit invocations, automatic routing, malformed inputs and missing capabilities.
- Publish using the existing source/release mechanism and verify the resulting content.

## Usage-driven evolution and cross-plugin ownership

When improving a workflow from history, combine usage-learning. Historical tasks and permissions remain evidence, not executable current requests. Keep private exports, account identifiers and chat links outside the distributable package. Record first-party generalized instructions separately from inherited external references and do not advance an upstream inspection date without a real new inspection.

Map a proposed gap to existing stages, profiles and companion plugins before adding another entry. Preserve explicit read-only/plan-only boundaries and the distinction between a portable recipe, a specialist lens and an actual native-host command. Adding metadata does not start a queue, install an agent or expose an unavailable tool. A domain companion retains its schema, tokens, import and release mechanics; this workflow coordinates evidence and handoffs.

For each changed route, test actual descriptors and behavior on realistic task prose, explicit controls, quoted historical commands, continuation, malformed input and missing capabilities. Preserve existing identifiers, aliases and host receipts unless a current authorized change explicitly revises them. Fresh task scenarios should receive the candidate instructions and task-local input, not the intended answer or a leaked diagnosis.

## Release integrity

Use the versioning convention of the plugin being updated.

Resolve the current owned source and exact release baseline through the available owning workflow. Compare the final effective manifest, skill discovery, references, prompts, connection/configuration, assets and retained files. For an overlay update, reason about both supplied and retained files rather than treating omitted files as deleted. Reconcile a release conflict against new source before retrying.

Inspect the actual generated distribution and its transitive runtime dependencies. Verify its documented standalone command from a clean extraction; a test passing only beside the authoring checkout does not prove a portable package. Keep optional host/core integration prerequisites explicit.

After an authorized save, read back affected source and report saved release separately from untested installation/activation. Instruction tests do not prove the user's host activated the new behavior. Use artifact-delivery and migration-release for their evidence boundaries rather than creating a parallel release ledger.

## Acceptance evidence

- Catalogue entries, handlers and supporting references resolve consistently.
- Existing identity, scope and supported explicit invocations remain compatible.
- Saved package/read-back evidence is distinct from untested host behaviour.

## Existing capability integration

- Use the installed plugin-creator or skill-creator workflow for the component being changed.
- Use current platform instructions before generic upstream package examples.
- Use shared security and independent review stages; do not invent new tool permissions.

## Failure modes

- Do not claim a metadata change registered a native agent or started a background queue.
- Do not overwrite unrelated prompts, connection settings, sharing or assets.
- Do not treat a referenced upstream skill as an installed capability.
- Do not turn an upstream approval preference into a new session permission requirement.
