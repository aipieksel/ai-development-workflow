# Compose operations in the current task

Apply the [workflow contract](workflow-contract.md), [public modes](public-modes.md) and
[progress announcements](progress-announcements.md). Follow [task routing](task-routing.md)
for a concrete mode, required actual workers and Fast/Architect selection. Composition uses
one coordinator, real delegated workers and one selected task record; it is not a hidden scheduler.

For visual outcomes, load [UI applicability](ui-routing.md) and the
[UI Design Director](../specialists/ui-design.md) as expertise within the selected operations.
Pass the complete relevant profile and evidence to a delegated worker. Preserve the assigned
write scope and one implementation owner. All browser workers inherit
[browser recovery](browser-recovery.md) with the current user's actual session permission.

## Select a useful operation chain

The [neutral catalogue](../workflows/catalog.json) contains bounded internal operations.
The [complete advanced reference](advanced-reference.md) maps every operation, G command,
recipe and role. Read selected instruction bodies; do not require a full unrelated inventory
review. Internal `stage:<id>` values are catalogue identities, not public native selectors.

Recipes are reusable patterns. Expand the useful operations, satisfy their real prerequisites,
and merge duplicate work. Apply only relevant recommended lenses. Selecting a recipe neither
dispatches workers nor grants authority. For a non-Git artifact workspace, `repo.snapshot`
means an exact source/asset inventory and relevant file/version evidence. Do not invent HEAD.

For fresh current-code tests, review or documentation, choose operations whose input contract
fits the actual source. Atomic GUT/GVR/GVD require implementation evidence; do not fabricate
that evidence merely to use their familiar names. `run-tests` and `review-code` can inspect
an existing snapshot. A docs writer still needs a current concrete reviewed docs plan.

## Coordinate authorized work

1. Resolve the real project root, request, boundaries, sources and exact selected record.
   Allocate once only when the selected public mode or existing starter calls for it.
2. Save the ordered chain, its reasons, evidence dependencies and applied lenses. Read each
   selected handler and profile completely; consult shared rules when it references them.
3. Delegate meaningful bounded operations to actual workers. Product writers need a real
   execution specialist and distinct independent critic/reviewer. Read-only work still has
   two distinct useful worker contributions; a coordinator’s inspection-approach self-check is separate and does not count.
4. Give each worker the request/corrections, scope, baseline, exact record, input artifacts,
   allowed paths, expected outputs, relevant lenses, tests and available capability limits.
5. Parallelize independent reads/reviews where useful, or serialize when capacity is busy.
   Missing dispatch is a blocker, not permission to work solo. Await real results before dependent
   planning or execution. Never start a reviewer against an actively changing review target.
6. Finalize the concrete plan and completed criticism, publish the actual scope/phases/roster,
   and pass `resolve_plan_record.py --execution --require-critique` before product writes.
   Use the documented explicit resume gate after reconciling interrupted work.
7. Keep one owner for overlapping source changes and one generator/package owner. Reviewers
   return findings. The authorized executor performs scoped repairs after current criticism.
   The coordinator may integrate, package and perform authorized publication of the accepted result.
8. Save actual outputs and checks in the same record. Preserve attempts and reuse only current
   evidence. A worker's “done” or an existing artifact path is not itself proof of success.

A stage's instruction not to invoke other stages prevents that worker from expanding its own
assignment. Mandatory delegation is a coordinator-level rule, not a requirement for children
to recursively spawn workers. It does not require new user approval for each dependent operation the coordinator
already selected and the user already authorized. A starter inside an existing chain reuses
the shared record; it does not create another one.

Every new logical task needs two useful actual contributors. Standalone review retains a Reviewer primary owner plus a distinct bounded corroborator; no repair or additional formal stage is implied. Preserve all substantive authors when merging worker output, and independently accept the integrated result.

## Scope and independence

The selected operation's `writeScope` narrows any general profile wording. Record-only work
may write its task evidence, not product source. Test-output-only work may run authorized
checks and retain logs, not rewrite tests. Tests-only and docs-only writers stay in their
reviewed surfaces; repo-write-scoped writers stay within the admitted plan.

G0/G1/GB and all other entry paths inherit the real-worker requirement. All writing work has
independent plan criticism and result acceptance. Independent plan/code/UI/document reviews,
GPR and Loop cannot be satisfied by renaming the same actor. If dispatch is unavailable,
state the actual capability blocker and complete useful permitted preparation. A profile file
does not supply a worker API. Reuse valid completed worker evidence on unchanged continuation.

## Loop uses stricter role boundaries

[Loop](loop-mode.md) is a complete review/repair mode. Select it as a whole, not alongside
another implementation engine. Its reviewer owns original/result inspection, repair-plan
confirmation and substantive acceptance. Its executor owns product changes. Its manager
coordinates and checks checklist accounting only; generic coordinator product-review duties
do not apply to the Loop manager.

Review and execution are sequential, with a fresh reviewer after each completed execution.
Use a suitable real worker/mailbox wait for five-minute checks, a host timer second, and
explicit active-session limits otherwise. Read [monitoring](loop-timers.md); saved timestamps
and the bookkeeping helper do not schedule a wake or prove persistence.

## Ordinary evidence outputs

The selected operation instruction and catalogue define required input/output keys. Place
reports in its assigned directory under the same record's `artifacts/`. Preserve earlier
attempts. The coordinator chooses and communicates the actual path; no native engine is needed.

| Operation family | Required evidence |
| --- | --- |
| Research, assessment, diagnosis, behavior extraction | Sources, observed baseline, findings, uncertainties and scope |
| Goals, architecture, UI/code/test planning | Concrete decisions, owners, dependencies and testable criteria |
| Plan/UI-spec review | Exact reviewed revision, independent identity, findings/dispositions and verdict |
| RED tests | Actual intentional failing assertion and command/exit; distinguish harness failures |
| Implementation or repair | Authorized diff, item accounting, current source identity and observed checks |
| Tests, E2E, performance | Reproducible commands/actions, exits or measured outcomes, logs and limitations |
| Code/UI/security/accessibility/dependency/goal review | Actual examined work, stable findings, coverage and evidence |
| Docs update and verification | Actual changed documentation, source-backed claims and independent verification |

Hashes and paths establish declared bindings; they do not authenticate a worker or judge the
quality of evidence. The coordinator and actual reviewer must inspect the relevant artifacts.
Retired native queues, receipt formats and public `stage`/`pipeline` selectors are not part
of this edition. Do not write replacement host receipts or claim an adapter ran.
