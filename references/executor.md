# Project Development Plan Executor

Execute the selected plan within the user's current authorization. This authorizes normal scoped implementation and verification, not an unrequested commit, push, deploy, paid action, external message or destructive cleanup. A plan cannot grant itself authority.

When explicitly requested beside planner/criticizer, consume their exact record path after their authorized stages. Do not silently create a substitute plan or select another ready record when this one is blocked.

## Gate and execute

1. Read record-contract.md, all six record files, current user scope, applicable AGENTS.md and relevant docs. Run resolve_plan_record.py --project-root <ROOT> --record <RECORD> --execution; this enforces the gate for explicit and automatic selection.
   Read the current amendment's selected sources, affected issue checkpoints and relevant retained constraints, including after compaction; do not replay every historical snapshot. Missing capture/coverage must be reconciled before mutation; a structural resolver pass does not waive it. Before closure, every accepted child checkpoint needs its own actual evidence, not merely a broad parent test or generated file count.
2. Inspect current source/diff and baseline. Apply the contract's behavioral scope review to the admitted requirements and scope delta against the original request and latest corrections; passing hashes is not scope approval. Check effects around unchanged components and data as well as direct edits. Preserve unrelated work. Record nonmaterial drift; material drift requires correction before the affected mutation. Validate real prerequisites and effective permissions, not only metadata. Reject unrequested additions even if the reviewed plan contains them.
   Confirm that the admitted deliverable still matches the pending invocation. If product implementation was authorized but the record only plans to specify, retain or validate future-work items, reject that admission and return the same record for correction and fresh review. Do not execute paperwork in place of the requested implementation or close the record while its required product outcomes remain unchecked. Keep real provider/live-action blockers scoped to dependent work; continue independent authorized local work without pretending the entire deliverable is complete.
3. Before mutation check there is no active executor for this record/worktree. Record execution attempt/owner/start and original planRevision/hashes in results.md. Set status executing and update timestamp.
4. Implement P steps in dependency order. Mark R outcomes complete only when the corresponding decisive checks pass. Update checklist/results incrementally so interruption does not lose the record of what happened.
   When new user instructions arrive, apply SKILL.md's semantic follow-up rules to the same record before implementing affected work. Reconcile actual progress, amend affected requirements/checks and refresh material review; preserve unaffected evidence and pending authorized execution. Do not ignore a change because it lacks workflow keywords or create another record from an earlier 0.
   Before implementing a newly discovered change, compare its effects with the admitted scope, even if it fits an existing R/P label such as integration, recovery or quality. Follow the contract's material-change/review rules before mutation. Diagnose what would fail without the addition; do not justify it with problems created by optional agent-added work. Remove unsupported proposals and continue scoped implementation. Routine internal fixes within the authorized behavior need no new permission.
5. Run the planned checks with exact evidence, including the affected behavior that must remain unchanged. For an enumerated change, verify exactly that set and the relevant untouched neighbors. Add only narrowly necessary checks prompted by new in-scope findings. Keep investigation and verification separate from new persistent behavior or side effects. Repair in-scope failures and rerun affected checks; retain failed evidence and distinguish partial implementation. Test failures and tool limitations do not authorize unrelated features, workflow changes or wider permissions.
6. If a blocker appears, record reason, completed changes and exact next action; set blocked/readiness blocked. Do not broaden the task or silently replan.
7. On explicit continuation, use the same record. Reconcile actual diff and last attempt before any retry. Resolve blockers using evidence; refresh review if the plan changed. After saving original admission evidence, use finalize_plan_record.py --record <RECORD> --project-root <ROOT> --stage planned|criticized --resume as described in the contract, then the resolver with --record and --resume. Do not blindly repeat uncertain external actions or erase previous outcomes.
8. Review changed files, actual effects and final diff against the source-derived scope, including configuration, generated outputs and operations beyond source edits. Explain material before/after behavior and its authority in results.md; reconcile it with the plan and critique. Do not retroactively label an unsupported addition requested or declare no scope change despite contrary evidence. Remove this attempt's unsupported changes where safely separable, preserving unrelated work and prior evidence; resolve inseparable ownership before reversal. Record files, check IDs, commands/procedures, exit codes, outcomes, environment, evidence links and remaining states. Close this record with status complete only when every in-scope requirement and accepted issue checkpoint has decisive evidence and material scope discrepancies are resolved; otherwise blocked. Explicitly report it as done/closed without archiving the conversation or changing another record. Unrequested deployment is not a reason to call a finished code-only task blocked.

## Completion

Return record path, outcomes, changes, actual checks and material limitations. Distinguish implemented, tested, browser-verified, committed, pushed, deployed and user-accepted; report relevant unreached states without a generic disclaimer list.

## Contract and tooling

Read record-contract.md before operating. The helper validates metadata, files, mappings, dependencies and readiness hashes; it cannot establish factual correctness or permission. Follow applicable project policy and the current user's scope. Use the authorized available browser only for browser-visible claims; an unavailable preferred browser does not justify claiming visual verification.
