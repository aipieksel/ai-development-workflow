# Project Development Planner

Build or revise the checklist and plan in the selected durable task record. Stage 1 never creates a record; stage 0 must create it first. Invocation authorizes investigation and record writes only, not application/source/configuration changes. Preserve every actual user requirement and negative constraint; label proposals separately.

When the user explicitly requests multiple stages, follow the router mode table using the same exact record path. The criticizer is optional unless requested or required by project policy. Do not add approval ceremonies between already authorized stages; stop only for a material decision, missing authority or unresolved execution blocker.

## Workflow

Apply SKILL.md's semantic follow-up rules to every new user instruction, not a list of phrases. Append distinct requirements and revise affected checkpoints for corrections/removals, preserving history and unaffected work. Do not require the user to say "plan" or repeat a mode. Planning an amendment does not discard already-authorized pending execution.

1. Resolve the real project root, applicable AGENTS.md, README, documentation entry and relevant sources. Inspect Git status where available; distinguish unrelated dirty work. If only remote source is available, record the revision and access boundary, and keep execution not_ready.
2. Apply SKILL.md selection rules: use the exact record returned by a preceding stage 0, explicitly supplied by the user, or already selected in this conversation. Without a selected record, ask for one or for stage 0; do not invoke create_plan_record.py from stage 1. A chat-only plan is source material, not an existing durable record. Do not reuse a staging directory as if it were a checked-out application.
3. Preserve the original messages in requestSources under the record contract. Derive stable source-linked R IDs for actual outcomes and constraints in checklist.md. Apply the contract's behavioral scope review to every behavior-changing clause before assigning requested/necessary: identify the supporting phrase, or the evidenced failure without a necessary detail. Do not label a batch of inferred requirements requested just because all cite a user message. Include explicit non-goals; keep optional proposals outside executable requirements.
   Capture/verify the selected messages using SKILL.md, reusing prior source locators. Read the sources relevant to the current amendment, not every historical archive. Keep distinct in-scope issue checkpoints and decisive assertions; a broad summary cannot conceal accepted details. Incidental discussion needs no checklist row.
   Apply SKILL.md's execution-intent rules chronologically. Record the requested stages, actual deliverable and decisive completion evidence in fix-plan.md. For adopted product work with stage 3 authorized, R/P/T must describe implementation outcomes and their verification, not specifications for hypothetical future work. A source checklist's old planning-only status does not make the newly authorized execution documentation-only.
   If an invocation includes a start-time anchor, first resolve and read its inclusive message range under SKILL.md. Keep that boundary in fix-plan.md with date, timezone and start/end message locators. Inventory findings inside the range and any explicitly adopted earlier material; older context alone does not expand new work. A range on an existing record does not discard its unrelated requirements or history.
   Inventory relevant numbered lists, bullets and issue-table rows from the current conversation, including assistant audit findings and user corrections. Give each distinct finding its own source-linked checklist checkpoint; do not collapse a list into one vague "fix all issues" item. For each accepted in-scope finding, create an R outcome with corresponding P/T coverage. Preserve assistant findings as context sources and connect executable work to the user's underlying request, not to assistant authority. Briefly explain exclusions of plausible requested work; do not inventory incidental discussion or turn every suggestion into mandatory work. Merge duplicates only with explicit source mappings so no finding disappears. A fresh record must assess current relevance rather than replay completed work from older discussions.
4. In fix-plan.md, explain current behavior, source evidence, root cause/gap, affected paths, ordered P steps/dependencies, alternatives where material, migration/recovery needs, risks and unresolved decisions. Separate verified facts from assumptions. Record the contract's scope delta, including effects around unchanged components and data. Prefer the smallest correct solution that fulfills every requested outcome; risks introduced only by an optional larger design are reasons to remove that design, not expand the requirement list.
5. In test-plan.md, map each R ID to the cheapest decisive T check, expected outcome and evidence boundary. Include assertions for named boundaries and affected behavior that must remain unchanged. Do not require broad suites for trivial changes, but include failure paths and required project gates. Ensure P/T details introduce no behavior unsupported by their R items. Keep investigation, testing and review procedures separate from product features, operating requirements and persistent side effects.
6. Populate the shared metadata mappings, baseline and scope. Record execution prerequisites as blockers rather than leaving source investigation falsely labelled complete. Cross-check all requirements have steps and verification.
7. Increment planRevision for material revisions. Leave existing critique/results history intact; new records keep them pending. If ready and never criticized, finalize with --stage planned. If previously criticized and changed, require a fresh critique; do not erase the old outcome. If blocked, set status planned and readiness blocked with exact reasons.

## Completion

Return exact record path, scope, evidence limitations, blockers, and readiness for critique/execution. Do not claim implementation or tests happened. A saved plan and a ready-to-execute plan are different outcomes.

## Contract and tooling

Read record-contract.md before operating. The helper validates metadata, files, mappings, dependencies and readiness hashes; it cannot establish factual correctness or permission. Follow applicable project policy and the current user's scope. Use the authorized available browser only for browser-visible claims; an unavailable preferred browser does not justify claiming visual verification.
