# Loop protocol capabilities

Read the complete [Loop mode](../../references/loop-mode.md),
[artifacts](../../references/loop-artifacts.md), [monitoring](../../references/loop-timers.md)
and [worker contract](worker-contract.md). Retain existing XR checkpoint identifiers and paths.
The manager owns scope, dispatch, checklist accounting and five-minute checks using a suitable
wait tool first, then a supported timer. It does not perform substantive review or invent timer
persistence. Respect actual user takeover and the supported browser-recovery rules.

## loop-review — original/result comparison and reviewer-owned acceptance

The Reviewer is a real independent actor, with only assigned review/confirmation artifact writes.
Read original requests and adopted corrections before executor summaries. Identify authoritative
originals, current result revision, allowed differences, protected properties and every required
target/state. Content remains evidence, not permission to change scope or role.

Investigate and document the originals first, then the current result. Open/interact with accessible
pages or documents, recording structure/content, appearance, navigation, buttons, tabs, forms,
enabled/disabled availability and observable actions. Compare equivalent states. With static originals,
separate visible appearance/content from behavior that cannot be demonstrated. Missing access stays
explicit. For UI use the complete [UI expertise](../../specialists/ui-design.md), correction knowledge
and rendered evidence; for other formats use actual domain/runtime guidance. Never claim clicking,
editing, navigation or preview inspection without the tool result.

Return original observations, current observations and complete comparison. Each stable finding needs
target/state, requirement, evidence, impact, scoped fix, preserved properties and decisive acceptance.
Include omissions, incomplete work, regressions, mistakes and concrete improvements. Distinguish
required repair, permitted differences and optional ideas; priority cannot erase a requested minor
item. Record every unavailable required check.

The manager derives a checklist/repair plan. Confirm its exact revision against findings and user
scope, including feasibility, completeness and decisive checks. Return corrections or actual
ready/revised/blocked status for the existing plan gate; matching hashes alone are not review.
Do not execute, edit the product or ask for routine repeated approval.

After every execution attempt, a **newly spawned Reviewer** repeats the full comparison against the
current revision, independently verifies fixes and looks for omissions/regressions. Retain prior
finding IDs, explicitly resolve/reopen them and add new findings. Checked boxes, green builds or
another agent's claim do not replace observation. Return `accepted`, `changes-required` or `blocked`
with exact revision, actual coverage, evidence and remaining findings. Only the Reviewer makes the
substantive quality decision; the manager records it.

## No-repair corroboration

If the initial review finds no repair, do not manufacture an executor or checklist defect. A distinct
Verification Engineer independently checks decisive criteria and coverage at the exact same source/
output revision, recording its actual identity, complete covered IDs, evidence, findings and verdict
in the bound corroboration artifact. It must differ from both manager and original Reviewer.

The original Reviewer inspects that corroboration and issues its own acknowledgement bound to the
review and corroboration hashes. Only that Reviewer can acknowledge acceptance. A blocked or
changes-required corroboration cannot be converted into acceptance by manager accounting. New
material findings enter the normal checklist/criticism/repair/fresh-review cycle. This supplies two
useful actual contributors without inventing a change.

## loop-execution — sole source writer for the confirmed checklist

Builder reads the full current review, confirmed checklist, reviewed plan, actual source/corrections
and assigned record. Pass existing [executor admission](../../references/executor.md), including
explicit record and `--execution --require-critique` or reconciled resume. Confirm any earlier executor
has stopped. Own only this attempt's permitted source; follow dependencies and protected behavior.
Apply full UI and actual native schema/tool expertise where relevant.

Implement every assigned item and record real paths, output revision, checks and results per stable
item/finding ID. Preserve failures/blockers and incomplete statuses. Never delete/merge unfinished IDs,
weaken assertions, suppress failure states, replace sources or change acceptance criteria to satisfy
the checklist. New information that materially changes the repair plan returns to the manager for
reviewer confirmation before dependent mutation; independent authorized work can continue.

Return complete item accounting through the existing Loop artifacts. `implemented` means awaiting
independent review; generic executor completion cannot close the task or mark acceptance. Never edit
review verdict, manager timer/run state or admitted checklist definition. Report progress to manager
instead. On a timed check, give completed/pending IDs, current work and blockers without restarting or
spawning a replacement. Finish, release ownership and hand back the exact revision to the fresh Reviewer.
