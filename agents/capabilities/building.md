# Builder capabilities

Apply the [worker contract](worker-contract.md) and shared
[executor](../../references/executor.md). Product, test and project-documentation edits need
the actual current plan, independent criticism and admission. A capability is expertise;
the selected operation retains its exact write scope. Keep one writer per overlapping
surface and one integration owner. Author-run checks do not accept your own result.

## execute-plan — the admitted implementation

Consume the exact selected record and current reviewed plan. Use the existing resolver's
`--execution --require-critique`, or reconciled `--resume`, rather than recreating capture,
another build preset or speculative planning. Reconcile source/plan/operation drift before
dependent writes; record actual hashes and the original admission. A materially changed plan
needs targeted replan/review, not a quiet expansion. Preserve unrelated edits and maintained
owners, lifecycle, data, permissions and caller contracts.

Implement all authorized requirements in dependency order, using existing components and
conventions. Record modified paths, checks, exits, failures, source revision and blockers in
the selected implementation artifact such as `artifacts/implementation.md`. Reconcile the
existing checklist and results against actual evidence. Do not automatically deploy, push,
install high-risk dependencies or declare independent acceptance. A missing required input
blocks its dependent work; it does not authorize a different deliverable.

## fast-build — Fast Engineer, GB and Ponytail

Deliver the whole outcome with the least new code and repeated work. Keep the actual host's
selected model/provider and tool permissions; this capability does not install other Ponytail
skills or hooks. Small understood localized builds use GB/Ponytail. If shared/broad impact,
architecture or migration decisions emerge, report them before dependent changes so the
coordinator obtains Architect advice and renews the affected plan and criticism.

Read current evidence once and refresh facts affected by changes. Trace callers, runtime
registrations, generated inputs, configuration, exports and tests; filenames and zero textual
matches do not prove that a replacement is active or an old owner unused. Group compatible
items by owner and precondition. Extend missing shared capabilities once, then migrate callers
as a family. Keep `Item/family | Existing owner | Required change | Depends on | Check | State`.
Do not replace a delivery request with another inventory-only report.

Prefer project components/services, then platform or standard-library facilities, installed
dependencies and finally minimal clear new code. Keep layers and naming; preserve validation,
error handling, accessibility and lifecycle. Avoid wrappers, frameworks, duplicate owners and
optional flexibility without a demonstrated need. Inspect representative cases before a
scoped mechanical script/codemod, then inspect the complete diff. Cut over callers, manifests
and meaningful tests together. Remove old owners only after verified use of the replacement;
temporary bridges need an owner, removal condition and parity check.

Work through the complete dependency-ordered scope in one continuous run. Do not impose batch
counts from a transcript or create a new approval/record for every file. Use one plan and
critique for a materially unchanged strategy. Resolve in-scope prerequisites rather than
shrinking the goal. A real permission or product decision blocks only dependent work.

Run cheap decisive checks after meaningful groups, collect independent failures and fix shared
causes. Verify the real product contract before changing assertions. Never delete tests,
blindly accept snapshots or weaken expectations to pass. Deduplicate the required final suite
on the integrated result; refresh checks invalidated by a repair. Browser journeys still run
when needed to prove the request. Do not defer all checks or rerun unaffected suites after
every edit. Prefer the project's runner; the optional
[acceptance runner](../fast-engineer/references/acceptance.md) is a fallback for an already
reviewed check list, not proof of worker dispatch or complete coverage.

Speed retains the actual distinct plan critic and result reviewer. This bounded Builder does
not spawn a second team. Report implemented outcomes, checks and real limits against the full
goal; a passing fixture is not a live-host result. When a blocker repeats, act on its recorded
dependency or explain the missing input rather than repeat the same investigation.

## tdd — RED, GREEN, then scoped refinement

Start with an observable requirement, owning module and real callers. Choose the smallest
test that catches the requested failure using the existing project runner. Use meaningful
unit, integration or journey boundaries, deterministic fixtures and actual external interfaces.
Cover relevant errors, boundary values, isolation and persistence, following project thresholds.
Demonstrate intended RED, implement the smallest admitted GREEN, check adjoining behavior,
then refactor under passing tests. Preserve the current operation's edit permissions.

## write-red-tests — tests only

Consume an already reviewed plan and unchanged in-scope source. Inspect existing tests and
fixtures; add only the required narrow tests/fixtures. Do not change production code, APIs
or dependencies unless the user expressly authorized the necessary test dependency. Run exact
tests and prove failure due to the missing requested behavior, not syntax, unavailable tooling
or a broken pre-existing baseline. Keep earlier tests and unrelated work. Save test paths,
commands, environment, expected failure and logs in `artifacts/red-tests.md` or the selected
operation artifact. Intentional RED completes this stage only; it is not passed implementation.
If the intended failure cannot be established, return blocked.

## green-refactor — consume real RED

Use the selected reviewed plan and actual RED artifact. Re-run recorded failures to confirm
their precise cause, implement the smallest permitted production change, then perform only
in-scope refactoring and relevant regressions. Do not rewrite expectations, fabricate failure
or replace invalid RED evidence. A previously passing target or ambiguous baseline must be
reconciled before the GREEN claim. Record actual outcomes in the implementation artifact.

## fix-reviewed-defects — findings plus a reviewed repair plan

Use the exact approved finding IDs, current source and a concrete independently criticized
repair plan with scope, owners, dependencies and checks. Findings alone never admit source
writes. Repair through canonical owners, preserve unaffected behavior and refresh invalidated
evidence. Do not rewrite the reviewed source/plan retrospectively or accept your own repairs.

## cleanup — evidenced consolidation and repository hygiene

Inventory the assigned scope and verify caller paths before deleting files or branches.
Account for dynamic imports, runtime registration, build/generated inputs, user configuration
and compatibility. Use actual installed repository analysis tools rather than assuming knip,
depcheck or ts-prune exists. Distinguish disposable leftovers from reusable components,
licenses and externally used files. Migrate and verify living consumers before removal.
Keep changes reviewable, preserve unrelated edits, run decisive tests/build/installation when
appropriate, and report what was removed, evidence of non-use and remaining uncertainty.

## author-e2e — journey-test source

When the selected operation authorizes test authoring, write or maintain scoped journey tests
using the existing suitable framework and fixtures. Apply the
[browser-journey capability](verification.md) for real interactions, isolated data, accessible
selectors and failure evidence. GJ's test-authoring purpose does not silently grant unrelated
application repairs; GEA's separately admitted implementation scope remains explicit. Check-only
operations cannot acquire test-writing authority from this capability, and skipped/quarantined
tests never become passing evidence.
