# Documentation and delivery capabilities

Apply the [worker contract](worker-contract.md) and current execution admission before project
documentation or packaging-source edits. Use the existing record and verified project owners.
Preserve unrelated work, approved content, maintained tests, runtime dependencies and licenses.

## update-docs — verified documentation and handoff

Read actual source/diff, test results and documentation conventions. Update only claims and
instructions warranted by the selected operation and user scope. Do not assume a framework,
provider, package manager, AST utility or service feature exists. Use installed tools; examples
are not capabilities. Trace usage/setup, API/schema contracts, component catalogs, release notes,
examples and handoff instructions to their real owner. Create a codemap only when needed, with
real entry points and links.

Reconcile contradictions between source, package, installation and generated exports. Label
historical observations as dated history; one machine's old setup is not a portable guarantee.
Derive counts, versions, defaults and file inventories from current authoritative sources.
Document the concrete problem, new behavior, supported inputs/outputs, relevant constraints and
shortest verified usage. Validate executable examples, paths, relative links and package layout.
State different standalone/integration prerequisites and distinguish examples from executed
evidence. Unknown runtime checks stay unverified.

Preserve requested artifact format and identity. Avoid placeholder functionality, speculative
tools, unrelated tutorials or invented maintenance schedules. Public-facing text should not
expose credentials, raw conversations or internal implementation details without a user-facing
purpose. Record changed documentation, source/test evidence and limits in the selected artifact.
An independent Reviewer checks the exact final claims; writing docs does not authorize code
rebuild, publication, scheduling or other product edits.

## delivery — one exact complete package

Treat reviewed feature scope and verified platform conventions as authoritative. Trace lifecycle,
registration, templates, assets and dependency use before removing leftovers. Reuse the existing
packager and shared owners; no filename-based guesses about non-use. Keep one package owner and
allowlisted source inventory. Account for omitted/retained files when an external update overlays
the existing installation.

Check the actual delivery archive, extract it into a clean disposable target and exercise the
authorized supported lifecycle and relevant user/admin entry points. Preserve stored data through
upgrade, deactivation and removal; do not perform destructive or production actions without actual
authorization. Keep necessary regression tests and legal notices. Record exact archive identity,
commands, outputs, failures, fixes and remaining platform-access limits in the same task record.

Prepare the complete requested outputs and opening/install instructions. Follow
[acceptance evidence](../../references/acceptance-evidence.md) for independent package checks and
destination readback. Prepared source, built archive, saved release, installed host and live runtime
are distinct facts. Publication remains a separate already-authorized accepted-result action; this
capability never makes an unverified archive a release or grants a new destination.
